# evals

One suite per plugin, measured by `claude plugin eval`.

```
evals/<plugin>/<skill>/NN-<case>/prompt.md      the case: frontmatter, then the prompt
evals/<plugin>/<skill>/NN-<case>/graders/*.md   one grader per file
evals/<plugin>/<skill>/NN-<case>/case.yaml      only when a fixture must be copied in
evals/<plugin>/<skill>/NN-<case>/scaffold.sh    copies that fixture into the sandbox
evals/<plugin>/<skill>/fixtures/                shared fixtures, and any build.sh
evals/<plugin>/<skill>/triggering/              the probes, plus probe_fixture.sh
evals/<plugin>/results/<tag>.json               the committed record
```

The suites sit here, and not inside the plugins, because Claude Code copies a plugin's whole
directory into its install cache. A suite kept inside a plugin ships to everyone who installs it,
and a suite is roughly 20 times the size of the skills it measures. Each case names its plugin in
its `plugins:` frontmatter, so `claude plugin eval` still resolves the plugin from out here.

A triggering probe caps `max_turns` at 3 on purpose, so it is normal for one to end with
`Reached maximum number of turns`. A probe measures only whether the model reached for the skill in
its first moves, and a run that hits the cap is still graded on what it produced. Raising the cap
buys nothing and costs more.

Run them with [`scripts/run_evals.py`](../scripts/run_evals.py). See [Evals](../README.md#evals)
for the axes and the enablement requirement, and [`FINDINGS.md`](FINDINGS.md) for what the measured
sweeps established. `SWEEP.md` and `TRIGGERING.md` are generated by
[`scripts/eval_report.py`](../scripts/eval_report.py).

A `README.md` inside a suite records why its cases exist. Case discovery ignores it, because a case
is a directory holding a `prompt.md` or a `case.yaml`.

## How a case is graded

These rules come from Anthropic's [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
Follow them when you write a case or repair one.

**Grade the outcome, not the retelling.** When the deliverable is a file, a
commit, or a posted comment, point the grader at the artifact and not at the
message the run wrote about it. A run that claims a file it never wrote must
fail. `focus: files` shows the judge every file the run changed,
`focus: {source: file, path: X}` shows it one file, and `file_exists` with a
glob settles a path question with no judge at all. A side effect that would
leave the sandbox goes through a stub CLI, and that stub records the call. The
recorded call is the outcome, so grade `writes.log`, `posted-calls.log` or
`tracker-calls.log`, and never the run's own summary of what it posted. Reserve
`focus: trace` for how the run got there, and `focus: last_message` for what the
run told the user.

**Prefer a deterministic grader where one fits.** A literal string, a file path
and an absent line are all `regex` or `file_exists` questions. They cost
nothing, they never disagree with themselves, and the harness warns that a judge
gets noisy on a long input. Keep `llm` for what needs judgment.

**One dimension per grader.** A grader that requires five things at once
collapses five results into one bit and loses the partial credit that shows a
run getting closer. Split it. A long criterion is fine, and often better, when
the length draws the pass and fail boundary for the judge rather than adding a
second requirement.

**Do not mandate the path.** Grade what the run produced, not the tool sequence
it chose. A run regularly finds a route the case author did not think of. The
exception is a firing indicator, `tool_used: Skill`, which is the thing the
`behavior` and `triggering` axes exist to measure.

**Balance the set.** Every suite needs a case where the right answer is that
nothing is wrong. Without one, a suite only rewards finding problems, and it
scores a run that invents a defect exactly as well as one that reads the file
correctly. `review-skill/04-already-sound-skill` and
`review-feature-suite/04-sound-suite-no-fabricated-findings` are the pattern.
The `triggering` axis carries the same balance as its `fire` and `hold` probes.

**A case must be solvable, and the prompt must be honest about the sandbox.** A
case runs in an empty working directory that its `scaffold.sh` fills, so a
prompt that names `evals/fixtures/x` when the scaffold copies it to `./x`
measures a missing directory. Name the path the run will actually see. A grader
that checks a file the run cannot create, because no granted tool can write one,
is rejected by the harness before it runs.

**Read a verdict off three runs.** `scripts/run_evals.py` defaults to
`--runs 3`, and `scripts/eval_report.py` reports pass@k and pass^k from that.
`--runs 1` is a smoke run and not a measurement.
